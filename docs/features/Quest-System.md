# クエストシステム (Quest System)

## 1. 概要
本ゲームにおいて、プレイヤー（探索者、ダンジョン管理者、およびPKer）に対して短期的・中期的な目標を提供し、ゲームプレイの動機付けと長期的な成長サイクルを支援するための「クエストシステム」を提案します。

非対称マルチプレイヤー型ローグライクであるRogueFの特性を活かし、それぞれの役割（ロール）に応じた独自の課題を設定することで、ロールプレイの深化と経済循環の活性化を目指します。

---

## 2. クエストの分類と設計目標

各役割に最適化された3つのカテゴリのクエストを提供します。

### 2.1 探索者クエスト (Explorer Quests)
- **設計目標**: プレイヤーがさまざまなバイオームを探索し、異なる装備や合成レシピ、特殊なアクションを試すきっかけを作ります。
- **主なクエスト例**:
  - **特定のバイオーム突破**: 「氷雪バイオームの 5F を突破する」
  - **討伐ミッション**: 「特定の属性を持つモンスターを 10 体撃破する」
  - **合成とクラフト**: 「[合成システム](Synthesis-System.md) を使用して特定のポーションを 3 回作成する」
  - **生存と制約**: 「装備を装着せずに任意のフロアを 3 階層連続でクリアする」

### 2.2 管理者クエスト (Administrator Quests)
- **設計目標**: 単にダンジョンを構築するだけでなく、プレイヤーを惹きつけ、ショップを繁盛させ、罠やモンスターの配置を最適化する「経営シミュレーション」としての面白さを拡張します。
- **主なクエスト例**:
  - **ダンジョン拡張**: 「[マイ・ダンジョン](Functional-Specification.md) を 5 階層まで拡張する」
  - **撃破と罠設置**: 「[配置したトラップ](Trap-System.md) で侵入してきたプレイヤーを累計 5 回撃破する」
  - **経済活動**: 「[ダンジョン内ショップ](Shop-System.md) の累計売上ゴールドが 10,000G に達する」
  - **繁殖と遠征**: 「[繁殖システム](Monster-Breeding-System.md) で Tier 2 のモンスターを 3 回孵化させる」

### 2.3 PKerクエスト (PKer Quests)
- **設計目標**: 侵入（介入）プレイにおけるバリエーションを増やし、プレイヤーとの適度な緊張感を持った非対称な交流（エモートやスタンプ等）を活性化させます。
- **主なクエスト例**:
  - **侵入と撃破**: 「レベル 10 以上の探索者を 3 回撃破する」
  - **コミュニケーション**: 「侵入中に [エモート・スタンプ](Emote-Stamp-Master-List.md) を累計 5 回使用する」
  - **サバイバル帰還**: 「HPが 20% 以下の状態で、倒されずに自分の世界へ帰還する」

## 3. クエストのライフサイクルと進行管理

クエストは以下のサイクルに沿って管理されます。

1.  **出現と受注**:
    - クエストは拠点の「ギルド（Guild）」または管理者・PKer用の各メニュー画面から確認・受注できます。
    - 受注枠は最大 3 つとし、プレイヤーが能動的に選択して進行させる形式（アクティブクエスト）を採用します。
    - 一部のストーリークエストは、特定の [ストーリー・世界観システム](Story-Lore-System.md) の進行に応じて自動的に受注されます。
2.  **進行状況の追跡**:
    - ゲーム内の特定のイベント（モンスター撃破、アイテム取得、ダンジョンクリア等）が発生した際、バックエンド側でイベントログを解析し、アクティブクエストのカウントを自動的に進めます。
    - 詳細は [イベントログ詳細仕様](../implementation/Event-Log-Schemas.md) のデータ形式に準拠して進捗が検証されます。
3.  **達成判定と報告**:
    - 進捗が 100% に達すると「完了（Completed）」状態になります。
    - 拠点のギルド施設、または各メニュー画面から「報酬を受け取る」を選択することで、報酬が獲得され、クエストは「受取済み（Claimed）」となり、新しいクエストを受注できるようになります。

## 4. データ構造と TypeScript 型定義

クエストの構成情報、および進行状況を管理するためのデータ構造です。
本仕様に基づき、[Player型定義](../../src/@types/player.d.ts) に以下のデータ構造を追加します。

### 4.1 クエストマスタ設定 (QuestEntry)
各クエストの基本情報を表す不変の定義モデルです。

```typescript
interface QuestEntry {
  id: string;                                                 // ユニークID (例: 'slime_hunter_01')
  title: string;                                              // クエストタイトル (例: 'スライムハンター')
  description: string;                                        // クエストの説明文
  category: 'explorer' | 'admin' | 'pker';                    // 対象ロール
  targetType: 'defeat_monster' | 'clear_floor' | 'synthesize_item' | 'earn_gold' | 'trap_kills' | 'use_stamp'; // 目標アクション
  targetId?: string;                                          // 特定の対象ID (モンスター種別IDやアイテム種別ID等)
  targetCount: number;                                        // 必要な達成回数
  rewards: {
    gold?: number;                                            // 獲得ゴールド
    exp?: number;                                             // 獲得経験値 (探索者・PKer用)
    materials?: { typeId: string; amount: number }[];         // 獲得資材リスト
    items?: string[];                                         // 獲得アイテムのIDリスト (アイテムマスターリストに準拠)
    customStampId?: string;                                   // 特殊スタンプのアンロック
  };
}
```

### 4.2 プレイヤー進捗モデル (PlayerQuestProgress)
プレイヤー個人の受注状況や進行度を表す状態モデルです。

```typescript
interface PlayerQuestProgress {
  questId: string;                                            // 対象クエストのID
  currentCount: number;                                       // 現在のカウント
  status: 'active' | 'completed' | 'claimed';                 // 進行ステータス
  acceptedAt?: Date;                                          // 受注日時
  completedAt?: Date;                                         // 達成日時
}
```

## 5. 経済・エコシステムへの影響と報酬設計

クエストの報酬は、ゲーム内の流通制限や資源バランスに配慮して動的に管理されます。

- **サーキュレーション制限との統合**:
  - クエスト報酬としてレアアイテムが支払われる場合、[ドロップ品・出現システム](Loot-and-Spawn-System.md) で定義された「世界内の存在上限（サーキュレーション制限）」を遵守します。
  - 上限に達している場合は、代替報酬（同等の価値を持つゴールドまたは建築資材パック）が自動的に適用されます。
- **ゴールドとインフレ対策**:
  - クエストクリア時の獲得ゴールドは、過剰なゴールドインフレを引き起こさないよう、プレイヤーの現在のレベルや進行階層に応じて適正化されます。
  - 管理者クエストの報酬に「建築資材（magic_crystal 等）」を含めることで、[建築システム](Construction-System.md) へのスムーズなリソース循環を促します。

## 6. UI/UX設計方針

プレイヤーが迷うことなく目標を把握できるよう、以下のUIコンポーネントを設計・配置します。

- **クエストボード（拠点ギルド）**:
  - 探索者キャラクターが訪れることができる、拠点内のギルド専用画面。
  - 受注可能なクエストが一覧表示され、詳細情報、クリア報酬、難易度（推奨レベル）を確認できます。
- **サイドバー/HUDミニ進捗**:
  - ダンジョン探索中、現在進行中のアクティブクエストの進捗（例：「スライム撃破: 7/10」）がミニマップ付近に小さく表示されます。
  - 目標達成時には、探索画面を邪魔しない程度の簡易アニメーションとSEで「QUEST COMPLETE!」と通知します。
- **管理者・PKerダッシュボード**:
  - ダンジョン管理画面、およびPK参戦用のメニュー画面内に「専任クエスト」のタブを追加。
  - 自分のダンジョンの攻略ログを見ながら、同時にクエスト進捗も一元管理できます。
